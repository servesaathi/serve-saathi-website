# ServeSaathi Website — Design System & Working Method

**Stack** (as of 2026-08-25): Next.js 16 (App Router, TypeScript), Tailwind CSS
v4 (CSS-first `@theme` config in `src/app/globals.css`, no `tailwind.config.ts`).
Next 16 is new enough that training data may be stale on it — `AGENTS.md`
(imported above) is regenerated by `next dev` itself and points at
`node_modules/next/dist/docs/` for anything that looks off vs. what you
expect; read that before assuming an API is missing or renamed by mistake.
The design tokens below are implemented as CSS custom properties inside the
`@theme` block, not a JS config object — same values, different file.

This file exists so a fresh Claude session in this repo starts with the same
design understanding built up over many sessions on the ServeSaathi mobile
app (React Native/Expo, `../ServeSaathi`). Read it before touching any HTML/CSS
here. It captures the brand's actual design tokens (colors, type, spacing) and
— just as important — *how* to work correctly from this Figma file, so design
fidelity checks don't have to be re-learned from scratch.

**Heads up on the current repo content**: `index.html`/`style.css` right now
are an old placeholder "coming soon" page — Poppins font, a
cream/forest/gold/terracotta palette that does **not** match the tokens
below. Treat that as throwaway scaffolding to be replaced, not as the design
system to preserve or extend.

## What ServeSaathi is

A senior-care platform (React Native app + this marketing/product website).
The audience skews older and includes low-vision/accessibility-dependent
users, family members arranging care for a parent, and care-provider
partners. That shapes the design language: generous tap/click targets, high
legibility type, calm warm-but-not-childish color, and a *working*
high-contrast mode — not a decorative one.

### How to actually pull a design (do this, every time)

1. **Load the `figma-design-to-code` skill/guidance before calling
   `get_design_context`.** Skipping this produces code that ignores the
   target stack's own conventions.
2. Call `get_design_context` on the specific node you're implementing — not
   a guess, not a parent frame "close enough." Treat its output as a
   *reference*, not final code: it comes back as React+Tailwind regardless of
   target stack, and its inline CSS-variable **fallback values reflect
   whatever mode happened to be active when the tool resolved them — often
   the wrong one** for what you're building (e.g. a node rendered in dark/
   high-contrast mode can still show a light-mode fallback hex in the
   generated class name). Cross-check anything color-related with
   `get_variable_defs` on the same node, and trust *that* resolved value over
   the fallback shown in a class name.
3. Prefer hint sources in this order when present, earlier overrides later:
   Code Connect mappings → component doc links → design annotations →
   design tokens/CSS variables → raw hex (lean on the screenshot for intent
   here). Never skip straight to raw hex if a token exists.
4. Reproduce every icon/image from its actual exported asset — never redraw,
   simplify, or placeholder an icon. Preserve the asset's real aspect ratio
   and padding box, not just its visible glyph.
5. Before writing new CSS/components, check what already exists in this repo
   and reuse it. Don't invent a second button style, spacing scale, or color
   variable that duplicates one already defined.
6. Verify visually: pull the actual screenshot for the node you're building
   and compare, especially for anything with color, since that's the easiest
   thing to get subtly wrong (see point 2).
7. Work section-by-section against Figma, not the whole site in one pass —
   that's the pattern that actually caught fidelity issues on the app side
   (wrong shade of "muted", a token reused across two visually-different
   contexts, a component variant that looks fine until compared to the real
   frame).
8. If a value is genuinely ambiguous (Figma and a stated requirement
   conflict, or two frames use the same-named token for visibly different
   colors), ask rather than guess — but don't ask about things you can just
   go check in the file.

### High contrast (single fixed palette — not a dark-mode variant)

Sourced directly from Figma's own "High Contrast" section, not computed.
Deliberately **not** pure black/white: primary text is near-white
(`#F2F2F2`), secondary/placeholder text is a visibly distinct gray
(`#AFAFAF`) so hierarchy survives, and interactive text (links, counters)
keeps real brand green/orange rather than flattening to monochrome — that
hierarchy *is* the point of the mode, so don't build a version that snaps
everything to two colors by luminance (that was tried on the app and had to
be reverted — it destroys exactly the distinction the mode exists to
preserve).

this exact structure: light and dark are two real palettes crossed with
whichever surface is active; high contrast wins over both and always renders
this one specific palette regardless of light/dark OS preference.

## Typography

Brand typeface: **Atkinson Hyperlegible Next** (Regular 400 / SemiBold 600 /
Bold 700) — chosen specifically for legibility, not aesthetics; don't swap it
for a "similar-looking" web font without checking with the user first, since
the accessibility rationale is the actual point of the choice. Load it as
`@font-face` (files live in `ServeSaathi/assets/fonts/`) or find its Google
Fonts equivalent if self-hosting isn't set up yet — ask before substituting.

Never fake a weight with CSS `font-weight` layered on top of one of these
family files if using the real font files — pick the file that already is
that weight, or the browser/OS may synthesize a heavier "faux bold" than
the design intends.

Type scale (size / line-height, all px):

|---|---|---|---|
| H1 | 26 | 34 | 600 |

| H3 | 20 | 28 | 600 |
| H4 | 18 | 24 | 600 |

and weight discipline, not necessarily the literal max size.

## Spacing, radius, shadow

Spacing scale (px), name → value — use these as your CSS spacing scale
instead of arbitrary margins:

```
xs 4  · sm 8  · md 12  · lg 16  · xl 20  · xxl 24  · xxxl 32  · xxxxl 40  · hud 48  · giant 64
```

Radius — this isn't one global border-radius, it's a small vocabulary tied
to *what kind of element it is* (verified against the app's hi-fi frames):

| Element type | Radius |
|---|---|
| Buttons, selection cards, chips | 6px |
| Content cards (info/event/review cards, stat rows) | 8px |
| Text inputs, field-style tap targets | 10px |
| Bottom-sheet / modal tops | 24px |
| Pills (fully round) | 9999px |

Shadow: a soft, low-opacity elevation system, not hard drop shadows —
`0 1px 2px rgba(neutral-900, 0.08)` for small elevation, scaling up to
`0 8px 8px rgba(neutral-900, 0.16)` for the largest. There's also a subtle
"green glow" shadow variant (`rgba(forestGreen-500, 0.10)`, spread ~6px) used
sparingly for brand-forward elements — don't overuse it.

## Iconography & imagery

- Icons are simple two-tone or single-tone outline/filled glyphs, not photo-
  realistic — keep new icons consistent with that style rather than mixing
  icon families.
- Photography (when used) skews warm, human, real-people-not-stock-feeling —
  seniors and caregivers in genuine-looking settings, not sterile stock
  photography.
- The brand mark is a stylized two-person motif forming an "S" swirl (see
  `ServeSaathi/assets/logos/` for the exact lockups) — a tall stacked
  icon+wordmark version and a wordmark-only version both exist; use the one
  that fits the layout rather than squashing one into the other's aspect
  ratio.

## Accessibility is load-bearing, not optional

- Font size should be user-adjustable in a bounded range around a sane
  default (the app uses default±3pt in 0.5pt steps) — don't wire up
  "accessibility" as a token nobody can actually change.
- High contrast (above) needs to be a real, distinct visual mode reachable
  from wherever the app/site's settings live, not a one-off page.
- Any interactive element needs a real focus state and sufficient tap/click
  target size — this audience disproportionately relies on both.

## Working method summary (tl;dr for a new session)

1. Load the Figma design-to-code skill, then pull the actual node via
   `get_design_context` + `get_variable_defs` — never guess a hex or size.
2. Resolve color per the *current mode*, not whatever fallback a class name
   shows — cross-check with `get_variable_defs`.
3. Reuse this file's tokens (or the site's own Figma-derived ones once that
   file exists) instead of inventing new colors/spacing/radii ad hoc.
4. Build one section at a time, screenshot-compare against Figma, then move
   on — don't build the whole page speculatively and fix fidelity at the end.
5. Treat light/dark/high-contrast as three real, distinct palettes (high
   contrast is hand-designed, not computed) if the site implements theming.
6. Ask when something's genuinely ambiguous or contradictory; don't ask
   about things checkable in the file.
